## 결론: 길터줘에 바뀌는 것

1. **Pleos SDK를 전부 쓸 수 있다.** 공모전에는 아직 공개하지 않은 SDK까지 모두 제공한다 [37:02]. 개발 단계에서는 Vehicle·NaviHelper·STT·TTS·FusedLocation SDK를 매니페스트 권한 선언만으로 쓴다 [49:30]. 10/29 기준 문서도 열렸다 (FusedLocation 1.1.2, TextToSpeech 3.3.1, Vehicle 2.3.2). → 내 차 위치는 FusedLocation SDK, 음성은 TTS SDK를 1순위로 바꾸고, 안드로이드 표준 기능은 예비로만 둔다.
2. **앰비언트 라이트를 MVP에 넣을 수 있다.** Vehicle SDK의 Light 도메인에 앰비언트 밝기·색상·켜기 설정 API가 있다. 에뮬레이터에서 실제로 바뀌는지만 시험하면 된다.
3. **외부 서버 구조는 그대로 간다.** 외부 API를 섞어 쓸 수 있고 공용 네트워크 연결도 된다 [49:05]. Supabase와 스마트폰 송신 웹 구조에 걸림돌이 없다.
4. **시연은 에뮬레이터가 표준이다.** 실차 시연은 없고 검증은 에뮬레이터로 한다 [32:00]. 시연 경로를 재생하는 우리 방식이 심사 방식과 맞는다.
5. **주행 중 화면 표시는 아직 모른다.** isActivityDistractionOptimized 질문을 읽었지만 "상세 개발 질문은 정리해서 따로 전달"하겠다며 넘어갔다 [50:00]. → 양보 안내의 주 수단을 음성과 앰비언트 라이트로 두고, 화면은 보조로 설계한다. 이메일로 문의한다.
6. **AI로 개발해도 되지만 PT에서 직접 설명해야 한다** [31:30]. 구조를 단순하게 유지하고 코드 설명 노트를 함께 만든다.

## 핵심 판단 네 가지

**1. 주행 중 화면 표시가 막히는가 → 아직 모름. 막혀도 시연이 성립하게 설계한다**
- 설명회에서 답하지 않았다 [50:00]. 직접 설치한 앱은 isActivityDistractionOptimized가 false로 나온다는 참가자 보고가 있다.
- AAOS는 매니페스트 선언만으로 주행 중 표시를 허용하지 않고, 앱 설치 출처도 함께 보는 것으로 알려져 있다. 보고와 맞는 동작이라 실제로 막힐 가능성이 있다고 본다.
- 대응: 양보 안내를 음성(TTS SDK)과 앰비언트 라이트(Light API)로 먼저 전달한다. 화면은 주행 중 단순 화면(R-9)과 상단 알림(R-11)으로 보조한다. 에뮬레이터에서 직접 시험하고, 이메일로 문의한다.

**2. 에뮬레이터 위치를 바꿀 수 있는가 → 아직 모름. 대비책을 넣는다**
- 설명회 답변이 없었다. FusedLocation 문서(소개·위치 조회 페이지)에도 에뮬레이터에서 위치를 바꾸는 방법은 없다. 참가자 보고로는 시흥 좌표로 고정돼 있다.
- 대응: 에뮬레이터 확장 컨트롤의 위치 설정과 경로 재생으로 FusedLocation 값이 바뀌는지 가장 먼저 시험한다. 안 되면 수신 앱에 '시연용 내 차 경로'를 넣고 화면에 시연 모드를 표시한다. 실차 시연이 없고 에뮬레이터로 검증하므로 시연 경로가 심사 방식과 어긋나지 않는다.

**3. 표준 위치 API와 녹음 음성을 써도 되는가 → 쓸 필요가 줄었다**
- 직접 답은 없었다. 다만 외부 API 혼용 허용 [49:05]과 SDK 전부 제공 [37:02]을 보면 금지될 이유는 없다.
- 기술 활용성 점수와 FusedLocation 문서의 "표준 위치 권한 동작 보장 안 함" 문구를 보면 Pleos SDK가 1순위다. 표준 위치 API와 안드로이드 기본 TTS는 SDK가 에뮬레이터에서 안 될 때의 예비로 두고, 녹음 파일은 알림음에만 쓴다.

**4. Pleos 앱 + 스마트폰 송신 조합이 인정되는가 → 직접 답 없음. 문제될 가능성은 낮다**
- 채팅에 같은 질문이 있었지만 음성 답변은 없었다. 가장 가까운 답은 외부 API·공용 네트워크 허용이다 [49:05].
- 심사 대상은 Pleos 앱(APK)이고, 차량 특화 가치는 수신 쪽에서 나온다. 기획서와 PT에서 "Pleos 앱이 본체이고, 스마트폰 송신은 공공 GPS 연계 전 임시 수단이다. Pleos가 탑재된 긴급차량은 차량 앱의 송신 모드를 쓴다"로 설명한다.
- 이메일 문의 목록에 넣는다.

## 기획서에 반영할 점 (심사 기준별)

- **차량 특화성**: 같은 접근 알림이라도 차량 상태(속도·브레이크·방향지시등·기어)에 따라 행동 안내가 달라진다. 화면을 보지 않아도 음성과 실내 조명으로 전달된다. 스마트폰 앱으로는 할 수 없는 부분이라고 쓴다.
- **창의성**: 문제는 운전자가 사이렌을 늦게 듣고, 방향을 모르고, 어떻게 비켜야 할지 모른다는 것이다 (특히 교차로). 해결은 접근 방향·도착 예상 시간과 지금 할 행동 하나를 알려주는 것이다.
- **기술 활용성**: SDK별 핵심 기능 연결표를 넣는다. FusedLocation(내 위치·접근 판정), Vehicle Brake·TurnSignal(양보 행동 확인), Vehicle Light(앰비언트 경고), TTS(음성 안내), NaviHelper(경로 겹침 판단, 확장).
- **사업성**: 차량 기본 탑재형 안전 기능(OEM), 긴급차량 운용 기관과의 송신 계약(B2G), 구급차 GPS 송신 의무화(AiR, 민간 2026.10·공공 2027.10)에 맞춘 민간 구급차 연동. 사용 빈도가 낮은 앱이라 MAU 대신 '알림을 받은 차량 수', '양보 확인율' 같은 지표를 제안한다.
- **가산점**: 1차에 GitHub 저장소(소스 + APK Releases)와 에뮬레이터 시연 녹화를 함께 낸다.
